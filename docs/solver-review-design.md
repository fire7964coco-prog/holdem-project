## 1. 확정 원칙 (사장님 10-03 · 재론 금지 · 핸드오프 축어 기반)

1. **사람 먼저, 기계는 따라온다.** 사람이 쓰기 쉽고(필수 = 글 한 칸) 읽고 판단할 수 있게. AI 가독성은 승인 후기를 **서버 렌더 HTML**(승인 시 `revalidatePath`)로 내보내 얻는다. 참여 장치처럼 브라우저 로드만이면 봇에겐 빈 페이지.
2. **두 트랙** — ① 자발: 요청 없이 «자리»만(앱 메뉴·결과 화면 아래 한 줄 고정 + 3회 솔브 뒤 결과 아래 한 줄 1회 · 팝업·반복 없음 · 보상 없음) ② 이벤트: 배민식 «후기 쓰면 ○○». 같은 후기창, 이벤트 후기엔 «이벤트 참여» 꼬리표(표시광고법 · 참여 장치 §4-2).
3. **받는 곳 = 앱 안(쓴 직후) · 보이는 곳 = 그 로케일 랜딩.** 같은 Supabase(트레이너 기록 방식) · 랜딩에도 입력 한 칸(«질문 댓글»과 한 블록 · 종류 열로 구분) · 질문→운영자 답글→월 1회 FAQ 승격 루프.
4. **신뢰 장치** — «사용 확인» 배지(솔브·트레이너 횟수 = 우리만 증명 가능) · 날짜·기기 · 아쉬운 점 칸(선택) · **부정 후기 삭제 금지**(숨김 = 링크·욕설·광고만, 원칙을 상단에 명시) · 운영자 답글 · 요약 한 줄(«후기 N · 사용 확인 M · 많이 언급된 스팟») · 대표 2~3개 = «도움됐어요» 순(운영자 선정 아님) · 3개 미만 로케일은 목록 숨김.
5. **이벤트 보상** — 돈 안 드는 것은 전원(저장 슬롯 20→50 · 트레이너 배지 · 리더보드 표식 · 복기 우선 체험) · 기프트콘은 **추첨**(09-28 추첨 장치 재사용). 조건 = 글자 수가 아니라 **내용**(스팟 공유 링크 첨부 또는 보드·자리 언급). 부정 후기도 보상 대상. 상시(슬롯) + 시즌(월 1회 추첨 · 홀덤보이TV 연동).
6. **우리가 못 하는 말(«유료만큼 좋다» · 사실 시트 §5 비교 금지)은 유저가 한다** — 유도 흔적 금지.

**원칙을 어떻게 읽는가 (설계 해석 · 검산 반영)**
- 원칙 6 = «비교를 언급한 후기도 **지우지 않는다**»는 뜻이지 «우리가 그 말을 **퍼 나른다**»는 뜻이 아니다. 우리가 능동적으로 재게시하는 자리(영상·FAQ 승격·PWA 한 줄·발표·외부 인용)엔 비교 주장이 든 후기를 쓰지 않는다(표시광고법상 사업자가 후기를 광고에 활용하면 비교 실증 책임이 생길 수 있다 — 해당 여부 확인 필요 · 보상 후기면 더 위험). 랜딩 목록·대표 후기(자동 정렬)는 §10-J.
- 원칙 4 «숨김 = 링크·욕설·광고만»을 **승인 대기·답 없는 질문으로 우회하지 않는다** — 그래서 승인엔 기한이 있고(§4-1), 질문은 «답변 대기»로 바로 보인다(§4-2).

- 🔴 **자발 자리 문구는 늘 중립으로 고정한다** — 이벤트 기간에도 «후기 쓰면 ○○»를 이 자리에 붙이지 않는다(원칙 2-① «보상 없음»). 이벤트 안내는 **폼 안의 응모 체크 칸 옆**에만 둔다.
- 누르면 → **후기 폼**(폰 한 화면 · §2-3). 앱 안에서 바로 쓴다(본체로 이동시키지 않는다 — 쓰려던 사람이 페이지 이동에서 빠진다).
- 🔴 **개통 안 된 로케일에선 앱 폼·자리를 숨긴다**(§10-D). 접수만 받아 두면 보일 곳 없는 후기가 쌓여 방치된다. 로케일을 열 때 앱 측 허용 목록(1곳)에 추가.

### 2-3. 후기 폼 (앱·랜딩 공용 필드)

| 칸 | 필수 | 입력 방식 |
|---|---|---|
| 본문 | ✅ | 글 한 칸 · 10~600자(§10-H) · **링크 금지**(09-28 `LINK_PATTERN` 공용) |
| 아쉬운 점 | 선택 | 글 한 칸 · 0~200자 · 링크 금지 |
| 별점 | 선택 | 탭 1~5 (§10-B) |
| 스팟 첨부 | 선택 | **앱 안에서만** «지금 이 스팟 붙이기» 토글 → 공유 id가 별도 열로 들어간다(본문 링크 아님 · 링크 금지 규칙과 충돌 없음) |
| 공개 이름 | 표시만 | «이 이름으로 공개됩니다: ○○ [바꾸기]» — profiles 닉네임이 구글 표시명(실명일 수 있음)에서 자동으로 채워졌는지는 확인 필요(코드 1에서 확인) |
| 이벤트 응모 | 이벤트 기간에만 보임 | 체크(기본 꺼짐) + 보상 안내 한 줄 — 켜면 꼬리표 자동(§6) |

- **placeholder·안내 문구 규칙**: 솔버 수치·스팟·비교·기능 약속을 넣지 않는다(원칙 6 유도 흔적 · 사실 시트 §4 출시일 금지). 허용 예 = «써 보니 어땠나요? 좋았던 점도 아쉬운 점도 그대로 적어 주세요.» 12언어 문구는 사실 시트 §5로 검수.
- 로그인 = 기존 구글·카카오(카카오는 ko만 · 사실 시트 §5). 후기는 «글자를 남기는 행동»이라 로그인 요구가 09-28 원칙(§1-4)과 같다 — 솔브 자체는 계속 로그인 없이(«로그인을 허들로 쓰지 않는다»).
- 🔴 **로그인은 도메인마다 따로다** — 앱은 솔버 도메인 localStorage 세션, 본체는 www 쿠키 세션. 같은 계정이어도 앱과 랜딩에서 각각 로그인한다(안내 문구에 반영). Supabase redirect 허용 목록에 두 도메인이 모두 있는지 = 미확인(코드 1).
- 기기 = 자동(폰/태블릿/PC — UA에서 세 값만 · 모델명 저장 안 함).
- 1인 1로케일 1후기 · 본인 수정 가능(«수정됨» 표시) · 본인 삭제 가능 — 단 추첨 끝난 응모 후기는 «삭제» 대신 **«비공개로 돌리기»**(추첨 기록 = 회차·user_id만 남는다 · 개인정보보호법 삭제 요구권과 추첨 검증 가능성을 같이 지킨다).

## 3. 데이터 모델 초안 (`supabase/solver-reviews.sql` 신설 예정)

09-28 `tournament_reviews`를 **재사용하지 않는다** — 키(대회 id ↔ 로케일), 종류(후기/질문), 사용 확인, 답글 구조가 다르다. 대신 규칙(RLS on · 정책 0 · 쓰기는 본체 서버 코드만 · 링크 거부 제약)은 그대로 따른다.

```sql
spot_shares (                                -- 코드 1 SQL에 같이 만든다(FK 대상)
  id text pk,                                -- 짧은 id (서버 생성)
  payload text check (char_length ≤ 16384),  -- 앱 디코더 상한과 같게 (solver/src/spot-share.ts:127)
  meta jsonb,                                -- 🔴 서버가 payload를 디코드해 만든다 · 클라이언트 meta 받지 않음
  ip_hash text, created_at
)
solver_feedback (
  id uuid pk,
  user_id uuid references profiles(id) on delete cascade,   -- 09-28 participation.sql과 같은 정책
  locale text,                                -- 보이는 랜딩
  kind text check (kind in ('review','question')),
  body text check (len 10..600 and 링크 거부),
  downside text null check (len ≤200 and 링크 거부),
  rating int null check (1..5),
  device text null check (in ('phone','tablet','desktop')),
  source text check (in ('app','landing')),
  spot_share_id text null references spot_shares(id),
  usage_trainer_days int, usage_trainer_n int, usage_solves int null,  -- 작성 순간 서버가 센 스냅샷 (§5-1)
  is_event_entry bool default false, event_round text null,
  status text check (in ('pending','public','hidden','private')),     -- private = 본인이 비공개로 돌림
  hidden_reason text null check (in ('link','abuse','ad')),          -- 이 3개 말고 숨길 수 없다
  status_changed_at timestamptz,
  created_at, updated_at
)
create unique index … on solver_feedback (user_id, locale) where kind = 'review';
create unique index … on solver_feedback (user_id, event_round) where is_event_entry;   -- 로케일을 바꿔 여러 번 응모 방지
solver_feedback_replies (id, feedback_id, body, created_at)            -- 운영자 답글만 (requireAdmin)
solver_feedback_helpful (feedback_id, user_id, created_at, pk(feedback_id, user_id))  -- 로그인 1인 1표 (§5-4)
```

- 🔴 `hidden_reason`이 3값뿐인 것이 «부정 후기 삭제 금지»의 **코드 수준 장치**다. 관리자 화면엔 «부정적이라서» 같은 선택지도, 삭제 버튼도 없다.
- `helpful_count`는 비정규화하지 않는다 — 집계 뷰로 센다(일관성).
- 이벤트 추첨 = 09-28 `review_event_draws` 재사용(키 열이 text라 회차 id `solver-2026-11`이 그대로 들어간다) · 블록 고정 방식 그대로.
- 랜딩 공개 목록 = `status='public'`만 반환하는 뷰(명단·user_id 노출 없음 · 표시 이름은 profiles 닉네임).

### 3-1. 쓰기 경로 — 검사는 한 벌만 (TS)
- **랜딩** = 본체 서버 액션(09-28과 같음).
- **앱(다른 도메인)** = 본체 **`/api/solver-feedback`** 하나로 일원화: CORS는 `solver.holdemmaster.com`만 허용 · `Authorization: Bearer <Supabase JWT>`를 서버가 검증 · 길이·링크·속도 제한·사용 스냅샷 계산을 **서버 액션과 같은 TS 함수**로. Supabase RPC(security definer)로 앱이 직접 쓰는 안은 기각 — 검사가 TS와 plpgsql 두 벌로 갈라진다.
- 공유 링크 저장도 같은 방식 `/api/spot-share`(로그인 불필요 → IP 해시 속도 제한 · payload 디코드·검증은 솔버 `spot-share.ts`의 `fromBase64Url`·`validSharedLines` 로직을 본체로 이식 · 검증 실패면 저장 거부).

## 4. 노출·숨김·운영

### 4-1. 후기
- 공개 방식 = §10-A. 승인제를 택해도 **처리 기한 72시간 — 넘기면 자동 공개**(대기로 묶어 두는 것이 사실상 선별 게시가 되지 않게). 관리자 화면 맨 위에 «대기 n건 · 최장 경과 n시간».
- 쓴 사람은 자기 후기를 «검토 중 · 72시간 안에 공개됩니다»로 본다.
- 숨김은 사유 3개만 · 사유를 기록하고 **작성자에게 알린다**(사이트 알림 · 이메일 발송 안 함) · 이의 = 같은 화면에서 «다시 검토 요청» 1회.
- 사유 정의(고지문에 그대로): **링크** = 외부 주소 · **욕설** = 특정인 비하·비속어(제품에 대한 강한 비판은 해당 없음) · **광고** = 다른 서비스·상품 홍보.
- 운영자 답글 = 관리자 화면에서 한 칸. 부정 후기 답글은 **해명이 아니라 사실**(개선 검토면 «검토 중», 안 하기로 한 것은 이유 — 예: 멀티웨이는 안 한다, 사실 시트 §2). **출시일·기능 약속 금지**(사실 시트 §4).

### 4-2. 질문 → FAQ 승격
1. 질문은 **바로 «답변 대기»로 공개**(숨김 3사유만 적용). 답 없는 질문을 비공개로 두면 운영자가 질문을 고르는 셈이 된다.
2. 운영자 답글이 달리면 «답변»으로 바뀐다. 랜딩엔 최근 3개 + 전체(details).
3. **승격 = 같은 질문이 3건 이상 모였을 때만**(달력 주기 아님 — 로케일 × 월 다시 쓰기·FAQ252 일치 게이트·MB·검수장 판정이 매월 따라오면 1인 운영에 과하다). KO는 발생 시, 그 밖 로케일은 분기마다 묶어서.
4. 🔴 FAQ로 옮길 때 답은 **사실 시트 §5 문구 규칙**과 플레이북 §4-8로 다시 쓴다 — 답글 원문을 붙이지 않는다. 비교 주장이 든 질문·답은 승격하지 않는다(§1 해석).

### 4-3. 남용 방어
- 링크 거부: DB 제약 + 서버 코드 이중(09-28 규칙 · `LINK_PATTERN` 공용 · 게이트로 코드↔SQL 대조).
- 속도 제한: 사용자당 질문 10분 3개 · 공유 저장 IP 해시 1시간 30개(가정).
- 다계정(이메일 확인 OFF): 배지 조건의 «서로 다른 날»·계정 나이(§5-1)로 거른다 · 숨김은 3사유로만.
- 운영자·관계자는 «도움됐어요»를 누르지 않는다 · 관계자가 후기를 쓰면 «관계자» 표시(고지문에 명시).

## 5. 신뢰 장치

### 5-1. «사용 확인» 배지
- 🔴 **지금 서버에 있는 사용 기록은 트레이너뿐**(`trainer_attempts` · 로그인 사용자). **솔브(직접 계산)는 기기에서만 돌고 서버에 아무것도 안 남는다**(사실 시트 §1 · schema.sql 주석).
- 🔴 **그 기록도 본인이 직접 넣을 수 있다** — `trainer_attempts`는 본인 insert 정책이고 `client_id`·`played_at` 값을 클라이언트가 정한다(schema.sql:303-331). 행 10개를 손으로 넣는 건 어렵지 않다. → «횟수만»으로는 증명이 아니다.
- 그래서 기준 = **기록 개수 + 서로 다른 날 + 계정 나이**(§10-E): 예) 트레이너 기록이 **서로 다른 2일 이상**(`played_at`이 아니라 `created_at` 기준) **그리고 계정 생성 7일 이상**. 작성 순간 서버가 세어 스냅샷 저장.
  - 🔴 `created_at`도 지금은 위조 가능하다 — `default now()`일 뿐이라 insert 때 값을 직접 넣으면 덮어쓴다. → 코드 1 SQL에 **`trainer_attempts` before insert 트리거로 `created_at := now()` 강제**(솔버 트레이너 동작 영향 없음 — 앱은 `played_at`을 쓴다 · 솔버 측에 통지). 이 트리거 전에는 «날짜» 조건도 증명이 아니다.
  - 그래도 «여러 날에 걸쳐 행을 넣는» 위조는 막지 못한다 — 배지는 «증명»이 아니라 «문턱»이다. 그래서 화면 문구를 낮춘다(아래).
- 솔브 횟수(§9 요청 ① 선택 항목)는 **보조 지표**로만 — 기기가 올리는 숫자라 단독 근거로 쓰지 않는다. 받게 되면 저장하는 것은 **횟수·시각뿐**(스팟 내용 아님 — 랜딩 FAQ «직접 계산한 스팟은 이 기기에만 저장»과 충돌 없게). 시행 시 **랜딩 FAQ·개인정보처리방침 동시 수정**.
- 배지 문구 = «✔ 사용 기록 있음» · 설명(누르면) = «솔버 계정에 여러 날의 사용 기록이 있는 사람이 쓴 후기입니다» — **개인 사용 횟수는 공개하지 않는다**(수집 목적 = 판정 · 공개는 목적 밖). 판정 기준은 고지문 «기준 펼치기»에 공개(EU 옴니버스 지침의 «후기 진위 확인 방법 공개»에도 맞는다).
- «구매 확인»류 표현 금지(무료 도구).
- 원칙 4 문구 «사용 확인»과의 관계: 이름은 원칙 그대로 «사용 확인» 계열을 쓰되, 화면 문구는 증명 강도에 맞춰 «사용 기록 있음»으로 낮춘다 — §10-E에서 확정.

### 5-2. 날짜·기기
날짜(일 단위) · 기기 3값. «폰에서 느림» 같은 후기를 읽는 사람이 자기 상황과 맞춰 보게 하는 정보다.

### 5-3. 요약 한 줄 — 정본 형식 (이 표 하나가 정본)

`후기 N (이벤트 참여 K 포함) · 사용 기록 M · ★ 평균 x.x (보상 없는 후기 R개 기준) · 많이 언급된 스팟: ○○`

| 요소 | 보이는 조건 | 빠지는 조건 |
|---|---|---|
| 후기 N | 공개 후기 N ≥ 3 | N < 3 → 줄 전체 숨김 |
| (이벤트 참여 K 포함) | K ≥ 1 | K = 0 |
| 사용 기록 M | 항상(N ≥ 3일 때) | — |
| ★ 평균 | **보상 없는** 별점 후기 R ≥ 5(§10-B) · 보상 후기는 평균에 넣지 않는다 | R < 5 |
| 많이 언급된 스팟 | 스팟 첨부 공개 후기 ≥ 5 · 서버가 만든 `meta` 최다값 | 첨부 < 5 |

- 같은 정본 문자열(조건 포함)을 **PWA 설치 자리(§9 요청 ③)·`/s/` 미리보기·발표에 그대로** 쓴다 — 표면마다 다른 숫자를 만들지 않는다.
- 본문 텍스트를 기계로 읽어 스팟·감정을 집계하지 않는다.

### 5-4. 대표 2~3개
- 정렬 = «도움됐어요» 많은 순 → 같으면 사용 기록 있는 후기 → 같으면 최신. **운영자가 고르지 않는다.** 배지는 후보 «조건»이 아니라 동점 정렬 기준(솔브만 쓰는 사람이 구조적으로 빠지지 않게).
- 개수: 공개 후기 3~5개 → 2개 · 6개 이상 → 3개(가정).
- «도움됐어요» = **로그인 1인 1표**(익명 UUID는 저장소를 지우면 새로 생겨 대표 자리를 살 수 있다 — 색인되는 자리라 막는다). 보상 없음.
- 재정렬 = **기존 매일 재빌드 크론**(`vercel.json` `/api/cron/rebuild` 15:20 UTC)이 한다 — 새 크론 없음.
- 부정 후기도 후보다(걸러내지 않는다). 비교 주장 후기 = §10-J.

## 7. 색인·AI 가독성

- 랜딩은 SSG다(`app/solver/page.tsx` — `metadata` 정적 · 데이터 읽기 없음). 후기 블록 = **서버 컴포넌트, 쿠키 없는 admin 클라이언트로만 읽는다**.
  - 🔴 `lib/supabase/server.ts`(cookies() 호출)를 쓰면 랜딩이 동적 라우트가 돼 `.html` 산출물이 사라지고, `check-hreflang`·`check-directives`(`.next/server/app/*.html`만 본다)가 랜딩을 못 본다. → **게이트: 빌드 산출물에 개통 로케일 `solver.html`이 있는지** 확인.
  - `export const revalidate`는 넣지 않는다. 갱신 = ① 공개 상태 변경 시 `revalidatePath`(관리자 서버 액션 · 자동 공개 크론 · 즉시 노출이면 작성 경로) ② 매일 재빌드 크론.
  - 경로는 로케일 → 경로 매핑 함수 하나로(KO = `/solver` · 그 밖 = `/{locale}/solver`).
  - 빌드 env `SUPABASE_SERVICE_ROLE_KEY`가 Vercel 빌드에 없으면 경고 + 게이트 🔴(§5-5).
  - 정적 페이지 on-demand `revalidatePath`의 Vercel 실측 = **미확인** → 코드 1 배포 직후 라이브 확인 항목.
- «도움됐어요» 수는 클라이언트에서 갱신(색인 대상 아님 · 숫자 흔들림이 재생성을 부르지 않게).
- 🔴 **Review·AggregateRating 스키마는 넣지 않는다**(09-28 원칙 §1-2 유지). 자기 사이트 제품 후기는 구글 리뷰 리치결과 대상이 아니고(self-serving), 보상 후기와 섞이면 위험. **재판단 = 비보상 공개 후기 20개 뒤**(그때도 리치결과 기대 없음 전제).
- 기대하는 것 = 후기 본문이 롱테일 검색어를 사람 말로 담는 것 + AI 답변이 인용할 텍스트. 그래서 서버 렌더가 필수다.
- 질문 → FAQ 승격분만 FAQPage 스키마에 들어간다(기존 경로).
- 로케일마다 후기가 다른 것은 «의도된 차이»다 → `docs/locale-intentional-diffs.md`에 한 줄(코드 1 회차).
