## 1. 공통 원칙

1. **정적 글은 그대로, 장치만 클라이언트에서 붙인다.** 페이지는 SSG 그대로. 숫자·후기·코멘트는 브라우저에서 불러온다 → 처음엔 색인에 안 들어간다(핸드오프 결정 «색인 보류»). 가치가 확인되면 그때 서버 렌더를 판단.
2. **구조화 데이터 추가 없음.** `AggregateRating`·`Review` 스키마 금지(자기 사이트 후기 리치결과는 구글 정책상 대상 아님 + 보상 후기와 섞이면 위험).
3. **적은 숫자는 숨긴다.** 3 미만이면 개수 대신 «첫 번째로 …» 문구. 빈 가게처럼 보이지 않게.
4. **로그인 = 이미 있는 구글·카카오.** 새 인증 없음. 로그인 요구는 «글자를 남기는 행동»에만.
5. **링크 차단 + 관리자 숨김.** DB 제약(`http`·`www.`·`.com/` 등 거부) + 서버 액션 검증 이중. `/admin`에 «후기·코멘트» 탭(숨김 토글). 기존 `requireAdmin()` 재사용.
6. **쓰기는 서버 액션만**(기존 `app/community/actions.ts` 패턴). 브라우저에 쓰기 권한 없는 RLS.
7. 파일럿은 **KO만**. 로케일 확장은 파일럿 판독 뒤.

## 2. 대회 가이드 «참가 예정 → 후기» (파일럿 3편)

대상: `apl-seoul-2026-guide`(10/23~25) · `wpt-seoul-2026-guide`(10/30~11/9) · `gop-incheon-2026-ii-guide`(10/30~11/8).
🔴 **APL 개막이 10/23** → «참가 예정» 단계를 살리려면 **10/10 전후 배포**가 목표.

### 2-1. 키 = `lib/tournaments.ts`의 대회 `id`
글 slug가 아니라 대회 id(`apl-seoul-winter-circuit-1`·`wpt-seoul`·`gop-incheon-2`)로 센다.
→ ja 글(`korea-poker-trip-gop-wpt-seoul-2026`)이나 나중에 EN 글이 붙어도 **같은 대회는 같은 숫자**를 공유한다. 대회 보드(`/tournaments`) 카드에도 같은 숫자를 띄울 수 있다.
글→대회 연결은 이미 있는 `blogLink`/`blogLinkByLocale`를 역으로 읽는다(새 필드 불필요).

### 2-2. 날짜로 자동 전환 (KST, `event.startDate/endDate` 기준)

| 단계 | 기간 | 상단 바(한 줄 요약 바로 아래) | 목차 항목 |
|---|---|---|---|
| ① 참가 예정 | ~ 개막 전날 | `🙋 참가 예정 12명  [나도 참가]` (3 미만: «이 대회 가시나요? [참가 예정 표시]») | 없음 |
| ② 진행 중 | 개막 ~ 종료일 | `🔴 진행 중 · 참가 예정 12명` + «끝나면 후기를 남겨 주세요» | 없음 |
| ③ 후기 | 종료 다음날 ~ | `⭐ 후기 7  [후기 보기] [후기 쓰기]` (3 미만: «첫 후기를 남겨 주세요») | **«참가자 후기»** 추가 |

- [나도 참가]는 로그인 필요(1인 1회, 다시 누르면 취소). 비로그인이 누르면 로그인 → 돌아와서 자동 반영.
- 후기 섹션 위치 = 본문 끝 · 작성자 박스 바로 위. 목차의 «참가자 후기»가 거기로 스크롤.

### 2-3. 후기 폼 (폰 한 화면)

- **필수**: 본문 30~600자
- **선택(버튼 탭, 글자 입력 없음)**: 참가한 이벤트(메인/사이드/새틀라이트/구경만) · 결과(버스트/ITM/파이널 테이블) · 별점 1~5
- 🔴 **평균 별점은 후기 5개 이상일 때만 화면에 표시.** 스키마로는 절대 내보내지 않는다.
- 사전에 [나도 참가]를 눌렀던 사람의 후기엔 `사전 참가 표시` 작은 뱃지(검증은 아니지만 «미리 가겠다고 했던 사람»이라는 신호).
- 1인 1대회 1후기 · 본인 수정/삭제 가능.

### 2-4. 테이블 (신규 2)

```sql
tournament_attendance (tournament_id text, user_id uuid, created_at, primary key(tournament_id,user_id))
tournament_reviews (id uuid, tournament_id text, user_id uuid, body text check(len 30..600 and 링크 패턴 거부),
                    event_kind text null, result text null, rating int null check(1..5),
                    was_attending bool, is_hidden bool default false, is_event_entry bool default false,
                    created_at, updated_at, unique(tournament_id,user_id))
```
RLS: 읽기 = 누구나(`is_hidden=false`만) · 쓰기 = 서버 액션만. 개수는 `count` 뷰/RPC로(명단 노출 없음).

## 3. 전략 글 «당신이라면?» 투표 (파일럿 3편)

### 3-1. 모양 — 솔버 핸드 복기 시안의 빈도 바 그대로

```
┌ 당신이라면? ───────────────────────────────┐
│ BTN 오픈 · BB 콜 · 플랍 A♥7♦2♣ · BB 체크    │
│ AJ♠, 팟 5.5bb — 어떻게 하시겠어요?           │
│  [ 체크 ]  [ 33% 벳 ]  [ 75% 벳 ]            │
└────────────────────────────────────────────┘
      ↓ 누르는 즉시 (비로그인 OK)
┌ 독자 선택  (138명)        솔버 답          ┐
│ 체크   ███░░░░░  24%     ██░░░░░░  18%     │
│ 33%벳 ██████░░  61% ←나 ███████░  79%     │
│ 75%벳 █░░░░░░░  15%     ░░░░░░░░   3%     │
│ 해설 한 줄 + [이 자리를 솔버에서 열기]       │
│ 💬 한 줄 코멘트 (로그인) · 최근 3개          │
└────────────────────────────────────────────┘
```
- 색·막대 = 시안(`참고자료/시안_핸드복기_2026-09-28/`)의 `.freq-row`를 사이트 크림 테마로 옮긴다. «나» 표시는 브랜드 골드.
- 투표 수 **20 미만이면 독자 % 숨기고** 솔버 답만 보여 준다(«아직 투표가 적어요 · N명»). 3 기준은 투표엔 너무 흔들린다.
- 한 줄 코멘트 = 로그인 · 80자 · 링크 금지 · 최근 3개 + «더 보기».

### 3-2. 🔴 «솔버 답»은 반드시 실제 계산값 (§13 · 솔버 사실 시트 §5)
투표 질문은 **본문에 이미 솔버 수치가 적힌 자리**에만 건다. 수치는 글 본문과 **같은 출처·같은 숫자**(형제 글 인용 = 원문 복사 규율). 위젯 정의 파일에 출처 주석 필수.
→ 그래서 파일럿 후보는 «유입 상위 전략 글» 중에서도 **솔버 수치가 본문에 있는 글**이어야 한다(§6 결정 C).
MB-115(1,755 플랍 표)가 풀리면 C벳 필라가 가장 좋은 자리가 된다.

### 3-3. 정의는 코드, 표는 DB
- `lib/polls.ts`: `{ id, slug, spot, question, options[], solver: {freq[], sourceNote}, explain }` — 글 본문엔 `:::poll[poll-id]:::` 한 줄. 렌더러가 **질문·선택지를 정적 HTML로** 그리고(크롤러·JS 꺼짐 대비) 클라이언트가 결과를 붙인다.
- `poll_votes (poll_id, option_idx, voter_id uuid, created_at, unique(poll_id,voter_id))` — voter_id = 브라우저 localStorage의 익명 UUID. 한 사람이 여러 번 찍는 건 막지 못하지만 **상금이 없는 투표**라 동기가 약하다. 추가 방어 = 서버 액션에서 IP 해시 1시간 30표 제한(구현값 — 한 집·한 매장 공유 IP를 고려).
- `poll_comments (id, poll_id, user_id, body ≤80 · 링크 거부, is_hidden, created_at)`.
- 🔴 **투표에는 보상을 붙이지 않는다** — 붙이면 표가 오염돼 «독자 선택» 숫자가 무의미해진다.

## 4. 이벤트 재설계 — «매주 상시 로또» → «대회 시즌 후기 이벤트»

### 4-1. 구조

| | 지금 | 제안 |
|---|---|---|
| 회차 | 매주(ISO 주차) | **대회 1개 = 1회차** (파일럿 대회 3개) |
| 응모 조건 | 커뮤니티 글 1 + 좋아요 1 | **그 대회 후기 1편**(30자 이상 · 숨김 처리 안 된 것) |
| 응모 기간 | 월~일 | 대회 종료 다음날 ~ **종료 +14일** |
| 추첨 | 6/45 번호 맞히기(3개 이상 당첨) | **응모자 중 N명 추첨** — 같은 비트코인 해시 + 09-28 SHA-256 방식 그대로 → 응모 목록(작성 시각순)에서 인덱스 선택 · 누구나 검증 가능 |
| 질 보상 | 없음 | **베스트 후기 1명**(운영자 선정 · 기준 공개: 구체적 상황·숫자·다음 참가자에게 쓸모) |
| 당첨 표시 | 기존 `badge` | 그대로 `winner` 뱃지 + 후기에 «베스트 후기» 라벨 |

- 로또 방식을 버리는 이유: 당첨자 수가 매 회 운에 따라 0~다수로 흔들려 **예산을 미리 못 정한다.** «N명 추첨»은 예산이 고정된다.
- 매주 상시 이벤트는 `EVENT_OPERATION.acceptingEntries = false`로 **멈춘다**(과거 추첨 기록 페이지는 유지). 코드는 지우지 않는다.
- 크론: 대회별 추첨 시각을 설정 파일에 두고 기존 `app/api/cron/draw-event`를 «회차 id = 대회 id»도 받게 확장.

### 4-2. 🔴 표시 의무 — 보상 후기
경품 응모로 쓴 후기는 공정위 «추천·보증 심사지침»상 **경제적 이해관계 표시** 대상이다.
→ 응모한 후기엔 `이벤트 응모 후기` 라벨을 **자동으로** 붙인다(`is_event_entry`). 응모 체크를 끄고 쓴 후기엔 안 붙는다.
(이 판단은 정보 제공 수준이다 — 경품 규모가 커지면 사장님 쪽에서 확인 권장.)

### 4-3. 참가 예정 버튼엔 보상 없음
누르기만 하면 되는 행동에 응모권을 주면 숫자가 부풀어 «참가 예정 N명» 자체가 거짓 신호가 된다.

## 7. 착수 순서 (승인 후 · 한 회차 = 한 묶음)

**설계에서 바뀐 것**
- 후기 섹션 위치 = 본문 **바로 뒤**(관련 글·작성자 박스 앞) — 목차 «참가자 후기»가 가리키는 자리가 짧아진다.
- 투표 파일럿 = «유입 상위 전략 글»에 걸고, 솔버 답은 GTO 시리즈 글 표를 옮기며 그 글로 링크한다 — 유입 많은 글엔 솔버 수치가 없고, 수치가 있는 GTO 글엔 유입이 없어서(GSC 28일 실측).
